# Frontend Admin (dragz-admin)

**English** | [中文](README_CN.md)

A React 19 + TypeScript + antd 6 + Vite admin shell. Every business page is "backend menu driven":
the backend `/auth/routes` returns the menu tree, and the frontend uses the `component` field (shaped like `/system/user/index`)
to look up the real component in `src/router/page-map.tsx`. The frontend hardcodes no routes and does no menu trimming.

## Tech stack

| Concern | Choice |
| --- | --- |
| Framework | React 19 + TypeScript 6 (`tsc -b` strict mode) |
| Build | Vite 8 (rolldown) |
| UI | antd 6 + `@ant-design/icons` |
| Table | Self-wrapped `components/vxe-table` (based on vxe-table) |
| State | zustand 5 (`persist` to localStorage) |
| Request | axios (`src/api/request.ts`, unified envelope + automatic token refresh) |
| i18n | i18next + react-i18next (`src/i18n.ts`) |
| Testing | vitest 4 + jsdom + @testing-library/react |
| Lint | oxlint (no eslint/prettier config files, formatting by convention) |

## Common commands

```bash
pnpm install          # install dependencies
pnpm dev              # dev server :5279, /api proxied to 127.0.0.1:5280
pnpm typecheck        # tsc -b --pretty false, one of the CI gates
pnpm lint             # oxlint src
pnpm check:i18n       # copy gate: hardcoded Chinese + zh/en key alignment
pnpm test             # vitest run (single run, not watch)
pnpm build            # tsc -b && vite build, output in dist/
pnpm preview          # preview dist/
```

Connecting to another backend: `VITE_API_TARGET=https://xxx pnpm dev`. **Do not write a remote address into
`vite.config.ts` and commit it**, or everyone's `pnpm dev` will connect straight to that environment.

Before `pnpm build`, move the old `dist/` out of the way (`mv dist ../../_attic/dist-xxx`).
The local safe-delete protection blocks `rm -rf dist` when the file count is > 50.

## How a page comes into being

1. The **backend** declares `Permission` when registering a route; at startup the sync writes the endpoint as a button in `sys_menu`.
   The page menus themselves are maintained by the seed SQL or by "Menu Management" in the admin.
2. The **backend** `/auth/routes` returns the menu tree visible to the current user (menus of disabled plugins are already trimmed).
3. The **frontend** `AdminLayout` renders the menu tree as the sidebar, and hands each node's `component`
   to `page-map.tsx` to look up the component, dynamically importing it with `lazy()`.
4. A `component` missing from the menu map falls back to `pages/fallback` — no blank screen.

So adding a page **does not require touching the route table**; only:

- write the component under `pages/<module>/` and export it by name;
- register it in `router/page-map.tsx` as `'/system/xxx/index': named(() => import('@/pages/...'), 'XxxPage')`;
- add a page menu in "Menu Management" with `component` set to the same path;
- button permission codes used by the page are generated by the backend route sync; just tick them on the role authorization page.

`page-map.test.tsx` keeps the full list of `component` values used by backend menus and asserts that each is registered in
`pageMap`. Forget to register a new menu and this test case fails outright.

## Generic CRUD scaffolding

Most list pages don't hand-write tables and drawers; use `components/ResourceCrudPage` directly:

```tsx
<ResourceCrudPage
  title="User"
  endpoint="/system/user"
  columns={columns}
  fields={fields}
  createCode="system:user:create"
  updateCode="system:user:update"
  deleteCode="system:user:delete"
  paged
/>
```

`endpoint` is the resource root path; the component uses it to call `GET/POST ${endpoint}`,
`PUT ${endpoint}/:id`, `PUT ${endpoint}/:id/status`, `DELETE ${endpoint}/:id`;
for the other switches see `Props` (`tree`, `paged`, `cascadeStatus`, `loadDetailOnEdit`, `rowActions`,
`sidePanel` etc.).

It builds in pagination, the search area, the toolbar, row actions (`TableActionGroup` with overflow collapse),
the create/edit drawer (`FormDrawer`) and permission-code-driven button visibility. What's left on the page is just column definitions and form fields.

## Access control

Only an imperative check is provided; there is no declarative wrapper component such as `<Auth>`:

```tsx
import { hasAccessByCodes } from '@/stores/access';

const canCreate = hasAccessByCodes(['system:user:create']);
// Common usage: build the actions array, decide whether a button renders
```

- A permission code is the backend `sys_menu.code` (the button-type row), one-to-one with the route's `Permission`.
- If `accessCodes` contains `*`, or the user is a super admin, access is always granted.
- Hiding a button in the frontend is only a UX nicety; **the real enforcement is Casbin in the backend**. Do not make security assumptions on the frontend.

## Internationalization (i18n)

**Rule: every piece of text in the UI comes from the locale files; no hardcoded Chinese or English in code.**

- There are only two locale files, `src/locales/zh.json` and `src/locales/en.json`, and the **key sets must be
  identical**. `src/i18n.ts` only loads them and holds no copy.
- Only two languages exist, Chinese and English. The list lives in `src/constants/locales.ts`
  (`LOCALE_CODES` plus the antd locale map) and must match the backend registry in
  `internal/pkg/i18n/languages.go`: switching language sends that tag as `Accept-Language`, and the API
  answers with menus, roles, departments and other preset data in that language.
- **Static interface copy lives in the packs only and never goes through System Settings → Translations**:
  that page maintains English for preset data (menus, permission buttons, roles, departments, jobs,
  storage). Changing a button, label or hint is a code change.
- Keys are dotted and hierarchical: `<namespace>.<object>.<field>`. Existing namespaces: `common`, `validation`,
  `auth`, `layout`, `upload`, `shell`, `preferences`, `locale`, `crud`, `vxe`,
  `pages`, `preview`, `system.<module>.*` (users / settings / org / security / tools /
  content / plugins). New pages create `pages.<module>.*` or `system.<module>.*` per module.
- In components use the hook:

  ```tsx
  const { t } = useTranslation();
  <Button>{t('system.users.create')}</Button>;
  ```

- **Non-component modules** (utility functions, constant tables, axios interceptors, zustand stores) use
  `import i18n from '@/i18n'` and read it **at call time**: `i18n.t('validation.email')`.
  Do not evaluate at module top level (that leaves the old language behind after a locale switch).
- Interpolation: `t('auth.lockCountdown', { error, countdown })`, with the locale file holding
  `"{{error}}, retry in {{countdown}} seconds"`. When you need to embed `<strong>`/`<a>`, use
  `<Trans components={{ ... }}>`; do not assemble JSX by string concatenation.
- Dynamic key concatenation (e.g. `t('preferences.layoutName.' + value)`) is only for suffixes from a finite enum;
  the sturdier writing is to store the full key in the constant table. The gate skips keys ending in `.` and keys built with `+`,
  so you must guarantee zh/en alignment for those keys yourself.
- Exemption markers: `/* i18n-exempt-start: reason */ … /* i18n-exempt-end */`, only for
  content that is "not UI copy" (e.g. the icon hint words in `router/menu-utils.tsx` that match backend menu
  titles). Adding a marker requires explaining why in the PR.
- Gate: `pnpm check:i18n` scans `src/**/*.{ts,tsx}` (skipping `*.test.*` and
  `src/locales/**`); it fails on "Chinese in string/JSX text" or "key missing from either locale file".
  `tsc -b` does not check copy, so this one must be run separately.
- **What is not translated**: backend menu titles, button permission names, dict items, config item descriptions, plugin names and
  descriptions, notice bodies — these are content in the database, maintained by admins; see
  [backend/docs/CONVENTIONS.md](../../backend/docs/CONVENTIONS.md#text--i18n).
- Locale switching is persisted to localStorage by `stores/locale.ts`, which then calls `i18n.changeLanguage`;
  adding a language means changing the `LocaleCode` type, the `resources` in `i18n.ts` and these locale files at the same time.

## Request layer conventions

`src/api/request.ts` handles it all:

- the envelope `{ code, message, data }`; `code === 0 || code === 200` counts as success, anything else throws;
- on 401 it automatically calls `/auth/refresh` for token refresh, and concurrent requests queue behind the same refresh (`refreshTokenQueue`);
- only when the refresh fails and the endpoint is not a public one such as login/refresh does it show a global error toast and log out;
- business code uses only `apiGet/apiPost/apiPut/apiDelete`; never use the axios instance directly.

## Testing

- Unit tests and component tests sit next to the file under test, named `*.test.ts(x)`;
- `src/test/setup.ts` wires up `@testing-library/jest-dom` matchers and fills in the `matchMedia`,
  `navigator.clipboard` and `getComputedStyle` that jsdom lacks (antd/vxe-table need them);
- for assertions involving `message`/`modal`, prefer asserting the store or the rendered result rather than toast text.

## Known constraints

- **No code splitting**: the single `index--*.js` bundle is about 840 kB (244 kB gzip) and the build warns. To optimize, start from
  `manualChunks`; don't change `chunkSizeWarningLimit` just to silence the warning.
- **No eslint/prettier config files**: formatting consistency relies on oxlint + human review; don't add a set of
  formatting config that conflicts with the existing code style.
- **The menu component is a string contract**: keys in the frontend `page-map.tsx` must match the database
  `sys_menu.component` character for character; rename both sides together.
