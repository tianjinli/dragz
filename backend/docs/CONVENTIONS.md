# Backend conventions (Simple Admin alignment)

**English** | [中文](CONVENTIONS_CN.md)

## Layers

- `internal/httpapi` — thin handlers (parse request, write response)
- `internal/httpapi/logic` — business orchestration; handlers must not call `store` directly for migrated modules
- `internal/store` — data access via repository interfaces; PostgreSQL implementation may use `internal/store/sqlc`
- `internal/pkg` — shared errors, i18n, ctx keys, casbin wrapper

**Rule:** `logic` and `httpapi` must not import `internal/store/sqlc` (generated code stays behind store interfaces).

## Text & i18n

**Rule: no user-facing text is written as a literal in Go code.** Every label,
message and error goes through a message ID, and both locale files carry it.

- Store returns sentinel errors from `internal/store/errors.go`
- HTTP mapping uses `internal/pkg/errors/mapper.go` and returns **message keys**, not prose
- `fail` / `failData` accept i18n keys only; localization happens in `localized()`
- Locale files: `internal/pkg/i18n/locale/{zh,en}.json`; **every key must exist in
  both**. `scripts/check_fail_i18n.sh` verifies the `errors.*` keys passed to
  `fail`/`failData`, the IDs passed to `i18n.StoredMessage` and the
  `login_log.reason.*` values are present in `zh` and `en`, so a typo can never
  ship a raw key to a client.
- Prefer `errors.*` keys; parameterized copy uses go-i18n `TemplateData` (e.g. `{{.Remaining}}`)
- Use `localized(r, ...)` for anything returned inside a response body; it needs
  the request to carry the translator (any route registered through
  `kernel.Register` does).

### Text written to the database

Rows that outlive the request (login log failure reasons, plugin last errors)
must not store rendered Chinese/English either:

- Store the message ID: `"login_log.reason.invalid_credentials"`.
- With template data, store `i18n.StoredMessage(id, data)`; it records
  `i18n:{"id":...,"data":{...}}` in the text column.
- Render with `localizedStored(r, value)` at read time. Plain text written by an
  older build is returned unchanged, so the switch needs no data migration.
- Logs, `fmt.Errorf` wrapping and other operator diagnostics stay in English
  (ASCII) and are never localized — they are read by developers, not by users.

### Three layers of text: chrome / preset data / admin content

The same sentence can come from three different places. Decide which layer it
belongs to before changing it:

1. **UI copy** — chrome shipped in the binary (buttons, form labels, hints).
   Message keys in `locale/{zh,en}.json`, both files, checked by
   `check_fail_i18n.sh`. **Never routed through translation management**: the
   page has no entry for interface copy, and changing such text means a code
   change plus a release.
2. **Preset data** — menus, permission buttons, roles, departments, scheduled
   jobs and storage configs created by migrations or plugin seeds. Chinese is
   the **default language** and stays inline in each table's text column;
   English lives in `sys_translation` (unique on `(entity_key, 'en')`), managed
   from System Settings → Translations, keyed by `menu.<code>` /
   `perm.<code>` / `role.<code>[.remark]` / `dept.<code>` / `job.<code>` /
   `storage.<type>`. Typing the Chinese source fills the English column through
   a free machine-translation service (`POST /api/system/translations/translate`,
   providers from `Translate.Providers`, no API key) and the result stays
   editable; a create that arrives with a blank English column is translated
   server-side, so an operator only ever has to write the Chinese. Both columns
   also carry a **Translate** button, which re-translates the other side on
   demand and replaces what is there — the automatic pass only fills an empty
   target, so it never overwrites a translation an operator already has. The
   service is best-effort — when it is unreachable the column is simply typed by
   hand.
   Clearing the English column deletes its row, and the delete endpoint answers
   **404** when there was nothing left to delete: the grid lists preset entities,
   so a row can outlive the translation it shows, and a silent "ok" would leave
   the operator looking at text that no longer exists.
   `localizePreset` overlays the request language via
   `i18n.Lang(r)`; a missing translation falls back to Chinese, and a Chinese
   request performs no lookup at all.
3. **Admin content** — dictionary types and items, config names/descriptions,
   notice bodies, user data: created on the fly, no stable entity code, and
   switching language must not rename them. The stored text is final.

The test: **ships in the binary → key; seeded business name → inline text plus
a translation row; created by an admin at runtime → plain text only.**

Button labels generated by `internal/menuperm` (action template + noun table)
belong to layer 2: the sync writes the English template into `sys_translation`
(`ON CONFLICT DO NOTHING`, so it never overwrites an edited translation).

### Language scope: Chinese and English

The product ships exactly two interfaces, so English is the only translation
target:

- `targetLanguages` in `internal/pkg/i18n/languages.go` is the **single source
  of truth** (today just `"en"`); both `Accept-Language` resolution and the
  write validation of translation management read it.
- The admin's language list in `frontend/admin/src/constants/locales.ts` must
  stay in step (`zh-CN` / `en-US`); the primary subtag is what goes out as
  `Accept-Language`.
- A request in an unregistered language reads Chinese, and writing a `lang`
  other than English answers 400.

Adding a third language: one entry in the registry, one in `locales.ts`, and a
way to enter that language on the translation page; interface packs are
separate (`locale/*.json` and the admin's `locales/*.json` per language,
otherwise that interface falls back to Chinese). **Data translation and chrome
translation are separate concerns** — do not use translation management to fill
interface copy.

Frontend copy conventions: [`frontend/admin/README.md`](../../frontend/admin/README.md#internationalization-i18n).

## Data access (sqlc)

- Engine: **postgresql only** for now (`sqlc.yaml`)
- **Business SQL lives only in `queries/*.sql`** — run `sqlc generate`; do not embed `SELECT`/`INSERT`/`UPDATE`/`WITH` string literals in `internal/store/*.go` (except generated `sqlc/`)
- Schema source should stay aligned with `migrations/` (see `schema/`)
- Docker Compose mounts `001_system_init.sql` (system base) for first-time Postgres init (`token_version` and `menu_parent_is_descendant` are in `001_system_init`). Existing named volumes do not re-run init — DBs that predate those objects need a one-off `ALTER` / `CREATE FUNCTION` (or recreate the volume); see `schema/tables.sql` for the canonical DDL. `migrations/` holds only scripts that participate in database creation (001 / 009). Retired business scripts have been removed from the tree; the rows they used to seed are deleted at startup by `retiredModuleStatements` in `internal/store/plugin.go`.
- Adding another database: see [NORMS_GAP.md](NORMS_GAP.md) playbook — do not rewrite logic

### Soft delete and business keys

- Deletes are soft: business tables carry `deleted_at`, and every read filters
  `deleted_at IS NULL`.
- A business key (`code`, `username`, …) is therefore **unique among live rows
  only**: `CREATE UNIQUE INDEX uk_x ON t (key) WHERE deleted_at IS NULL`, never a
  `UNIQUE` table constraint. A plain constraint keeps a deleted row's key
  occupied, so "delete a record, then create it again" fails with a duplicate-key
  error. Postgres cannot express the partial form as a table constraint, which is
  why those indexes sit with the other `CREATE INDEX` statements, and why
  `bootstrapStatements` in `internal/store/plugin.go` carries the same DDL for
  databases that predate the change (it drops the old constraint first).
- Consequence for SQL: `ON CONFLICT (key)` no longer infers an index on those
  tables — write `ON CONFLICT (key) WHERE deleted_at IS NULL`, or revive the
  existing row and insert only when there is none (see
  `queries/menu_buttons.sql`).
- `sys_file` keeps a plain `UNIQUE (storage_id, object_key)`: its delete is a
  recycle bin with a restore path, and a restored file must not collide with a
  key reused in the meantime.
- Seeded rows carry **explicit ids** (`migrations/001_system_init.sql`), which
  leaves the owning sequence at its initial value; `seedStatements` re-syncs
  every serial id sequence on boot, otherwise the first row created through the
  UI collides with a seeded row (`sys_x_pkey`).

## Authorization

- Casbin policies: `(roleId, permissionCode, access)`
- Reload on startup, after role grant changes via `app.Context.AfterRoleGrantsChanged`,
  and on **both** plugin enable and disable (a disabled plugin's codes must leave
  the enforcer immediately).
- Permission cache in Redis keyed by user id
- Access JWT carries `token_version`; force-logout / password change bumps DB version so existing access tokens fail validation

## Permission buttons (API permissions)

Every permission code is a `sys_menu` row with `type = 'button'`. There is no
separate permission table and no second grant tree.

- **One code, one button.** `sys_menu.code` holds the permission string
  (`system:user:create`). `sys_menu.permission` was deleted: it was never
  populated and never read. Page codes (`system_user`) and permission codes
  cannot collide because the colon is a strict discriminator in `validateMenu`:
  button codes must contain one, every other type must not.
- **The route table is the source of truth.** `plugin.Route.Permission` /
  `AnyOf` declare the codes; the startup sync (`store.SyncPermissionMenus`,
  driven by `internal/menuperm`) upserts one button per code after every plugin
  migration has run. Adding a route therefore makes a permission grantable with
  no seed change.
- **Owned vs editable.** `parent_id`, `method`, `path`, `is_sensitive`,
  `plugin_id`, `status` and `code` belong to the sync. An administrator may only
  change `name` and `sort`; `store.lockManagedMenuFields` overwrites everything
  else, and `UpdateMenuStatus` / `DeleteMenu` reject those rows outright.
- **`sys_menu.managed` is the ownership flag.** The sync writes `1` for every
  code the route table declares; the admin UI writes `0` (the column default).
  Only `managed = 1` rows are locked and only they are retired, which is what
  lets an administrator create a permission button by hand without the next
  boot deleting it. A hand-made button whose code later appears in the route
  table is adopted by the sync (`managed` flips to 1) because the route table
  owns the code. Hand-made buttons are ordinary rows: edit, disable, delete all
  work, and their type is pinned to `button` so they can never become a page.
  Their code is what a frontend or an external service can check; they grant no
  endpoint by themselves, since the guard reads the route's declared code.
- **Parent resolution is derived.** `system:dict:item:create` walks
  `system_dict_item` → `system_dict` and takes the longest candidate that exists
  as a real menu, so only exceptions need `Route.MenuCode`. A *core* route that
  resolves to nothing fails startup; a plugin route is skipped until its
  migration creates the page (enabling re-runs the sync).
- **Grants follow the code.** `/api/auth/codes` and the Casbin policy query both
  read `sys_role_menu JOIN sys_menu WHERE type = 'button'`, filtered by
  `(plugin_id = '' OR plugin enabled)` exactly like the menu tree. A disabled
  plugin's codes disappear with its pages.
- **Retirement is soft.** A sync-owned button whose route disappears is soft
  deleted and disabled, but its `sys_role_menu` rows stay: re-adding the route
  restores the grants. The upsert resets both `deleted_at` and `status`, because
  `ListUserPermissionCodes` filters `status = 1` — without the status reset the
  grants would come back attached to a dead button.
- **Legacy upgrade.** `store.migrateLegacyAPIPermissions` copies
  `sys_api_permission` into buttons, `sys_role_api_permission` into
  `sys_role_menu`, then drops the three legacy tables in one transaction. It is
  guarded by `to_regclass('public.sys_api_permission')`, so it runs once and is
  a no-op afterwards. Codes belonging to already-deleted modules are copied too
  and then removed again by `Seed`'s retired-module cleanup, which runs
  immediately after `Bootstrap`.
- **Frontend gating is coarse by design.** Menus / notices / hooks / API
  permissions use a single `system:xxx:manage` code for create, update and
  delete because that is what the route table declares. Do not invent `:create`
  / `:delete` literals in the UI; they would never be granted.

## API contract

- Hand-written `api/desc/all.api`; no goctl code generation required
- Entry point: `api.RegisterRoutes`
- Liveness: `GET /api/health`; readiness: `GET /api/ready` (DB + Redis)

## Scheduled jobs (asynq)

- **Configuration**: `sys_scheduled_job` in PostgreSQL remains the source of truth for the admin UI
- **Execution**: `cmd/jobs-runner` runs asynq Server + Scheduler (Redis queue)
- **API process**: `admin-api` only enqueues manual runs and reconcile requests via asynq Client; no 15s DB polling
- **Logs**: `sys_job_log` written by the jobs-runner on each attempt
- **Sync**: jobs-runner Reconciler loads enabled jobs every 60s and on `scheduler:reconcile` tasks triggered after CRUD
- **Feature flag**: `feature.scheduler.enabled` disables registration and execution

## Config

- `Database.Driver` defaults to `postgres` (only supported driver today)
- Production secrets must not use development defaults; see `config.Validate` and `etc/admin-api.example.yaml`

## Plugins (runtime enable/disable)

Layers: `plugins/ → platform/ → kernel/`. Dependencies point one way only;
`scripts/check-imports.sh` enforces it.

- **Registration is compile time.** `plugins/all/all.go` is the only switch.
  There is no hot loading: enabling a plugin changes behaviour, not the binary.
- **Import boundaries.** `internal/pluginstate` is the neutral boundary package
  (standard library only) and exists because `internal/plugin` imports
  `internal/app`; `app` and `store` must never import `internal/plugin`.
- **Ship dark.** A newly compiled non-builtin plugin is inserted with
  `enabled = is_builtin`, so it starts disabled and its migrations do not run
  until an administrator enables it in System Settings → Plugin Center.
- **Builtins cannot be disabled.** `system` is forced enabled in the catalog
  sync, in the in-memory snapshot, and in the `UPDATE ... WHERE is_builtin =
  FALSE` guard. `/api/health` and `/api/ready` therefore never 404.
- **Disabled means 404, not 403/503.** The route gate sits *outside*
  authentication, so an anonymous caller gets exactly the same response as for
  a path that does not exist. `rest.WithNotFoundHandler` renders the same
  envelope for unmatched paths.
- **Menus are pruned server-side.** `sys_menu.plugin_id` (`''` = core) is joined
  against `sys_plugin.enabled` inside the two recursive menu queries, so a
  disabled plugin takes its whole subtree with it and no orphan is promoted to
  a root. Both queries also filter `type <> 'button'`, so permission buttons
  never reach the sidebar.
- **Disable and uninstall are different operations.** `Disable` only flips the
  flag: no DDL, no data loss, instant re-enable. `Uninstall` is destructive and
  is allowed only on a plugin that is already disabled; it runs in one
  transaction and drops `Meta.DropTables`, the plugin's `sys_menu` rows (pages
  and buttons), its `sys_plugin_migration` rows and its `sys_plugin` row. The
  plugin stays compiled in, so the next startup re-inserts it as disabled and
  enabling replays migration `001`. Table names are interpolated into `DROP
  TABLE`, so they are validated against `^[a-z][a-z0-9_]{0,62}$` before any DDL
  runs — schema qualification, quoting and uppercase are rejected.
- **Every replica has its own snapshot.** `Enable`/`Disable` reload the replica
  that served the request; `admin-api` also runs `plugincenter.Watch`, which
  re-reads `sys_plugin` every 5 seconds so the other replicas converge without a
  restart. Worst-case staleness is one interval. Polling is deliberate: go-zero's
  redis client exposes no subscriber, and a one-row-per-plugin query is cheaper
  than a second connection plus reconnect/dropped-message handling.

### Bootstrap DDL vs migrations

- Plugin tables (`sys_plugin`, `sys_plugin_migration`) and the `sys_menu`
  columns `plugin_id`, `method`, `path`, `is_sensitive` are created by **runtime
  bootstrap DDL** in `store.PluginRepository.Bootstrap` on every startup. This is
  deliberate: the Postgres image only runs `migrations/*.sql` on an empty
  PGDATA, so a new migration file would require a manual `psql` step on every
  existing database.
- Everything else belongs in `queries/*.sql` (business SQL) or a plugin's own
  `migrations/NNN_*.sql`.
- **Removing a module** means three things: delete its code, delete its seed
  file, and add its rows to `retiredModuleStatements` in
  `internal/store/plugin.go`. The last step is what cleans up databases that are
  already initialised, since deleting a seed file only affects empty volumes.

### Plugin migrations

- Location: `plugins/<id>/migrations/NNN_name.sql`, embedded with `go:embed`.
  `NNN` is exactly three digits so lexical order is numeric order.
- **Append-only and immutable.** The SHA-256 of each applied file is recorded;
  editing an applied file fails the next enable closed (`ErrChecksumMismatch`).
  Fix forward with a new file. Break-glass is restoring the original file or
  deleting the bookkeeping row by hand.
- **One file = one transaction**, together with its `sys_plugin_migration` row.
  A failure rolls back only that file, so the next enable resumes from it.
- A file may contain **multiple statements** (executed with no bind parameters,
  which makes pgx use the simple protocol) but must not contain `$1`-style
  placeholders.
- Plugin-owned menus use IDs **1000+** and must set `plugin_id` explicitly.
- All schema changes are serialised by a session-level `pg_advisory_lock`
  (bootstrap, seed, catalog sync, startup migrations, enable, disable).
- **`admin-api` is the only migration owner.** `jobs-runner` must start after it
  has completed startup.

### Disabling

Disabling flips a flag: it never runs DDL and never deletes rows. Tables and
migration bookkeeping stay, so re-enabling is instant and lossless. Uninstall
(drop) and down-migrations are out of scope.

### Known limitation: multi-replica

The enabled-state snapshot is per process, so a toggle on replica A only
reaches replica B through `plugincenter.Watch`, which means worst-case staleness
of one 5-second interval (menus are read from the database, so they are
consistent, which makes the divergence visible if it lasts). A Redis pub/sub
invalidation channel or a short-TTL Redis key would remove the interval; both
were skipped because go-zero's redis client exposes no subscriber and a
one-row-per-plugin poll is cheaper than a second connection with
reconnect/dropped-message handling.
